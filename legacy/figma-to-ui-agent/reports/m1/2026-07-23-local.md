## 已实现合约

### DesignBundle

- Schema 版本、项目标识和正整数修订；
- Figma REST 来源、脱敏文件键哈希、目标节点和检查时间；
- Variables 的 `available` 与 `unavailable_optional` 能力状态；
- 页面、节点、组件、样式、设计值、截图、资产、来源追溯和警告；
- LocalImageRef 只允许项目内相对路径，文件名必须匹配 SHA-256，MIME 必须与扩展名
  一致；
- 页面根节点、父节点、组件、样式、设计值、图片和来源追溯引用全部闭合；
- 节点标识重复、父链循环、未知字段和不兼容版本失败关闭。

### 四工具

- `inspect_figma` 要求项目、Figma Design URL，并校验 URL 与显式目标冲突；
- `load_ui_spec` 只读取当前或指定不可变修订；
- `save_ui_spec` 要求完整 UISpec、`baseRevision` 和保存原因；
- `render_and_compare` 只接受项目内页面、视口、行为夹具和有界比较阈值；
- Preview URL 只允许无凭据的 localhost HTTP，验证产物只能位于项目 `runs/`；
- Provider 使用的 TypeBox 参数由同一严格契约对齐，不再接受任意 UISpec。

## Figma REST 与标准化

- 只允许 `https://figma.com/design/...` 和
  `https://www.figma.com/design/...`；
- Token 仅进入 `X-Figma-Token` 请求头，错误不保留 Token、文件键、响应正文或
  签名 URL；
- REST 请求有 30 秒默认超时、20 MiB 默认响应上限、禁止重定向、有限 429/5xx
  重试和最大 URL 长度；
- 页面候选、显式目标、布局、文本、组件、实例、Styles、图片来源、
  `boundVariables` 和不支持节点均有确定性归一化规则；
- 原始 Variable ID 只存在于检查过程的内存侧车数据，DesignBundle 只保存
  SHA-256 来源引用；
- 未选中组件不会生成指向项目外节点的 `nodeId`。

## Variables 策略

1. Variables API 可用时，保留真实变量名称、集合、模式、代码语法和别名来源哈希。
2. 401/403 时标记 `unavailable_optional`，优先从节点绑定的已解析值生成
   `inferred_from_binding` 设计值。
3. 不存在可用绑定值时，只把至少两个不同节点重复使用的颜色、间距或排版数值生成
   `inferred` 设计值。
4. 推导值使用项目内点分名称，不伪造 Figma 集合、模式或代码语法。
5. 别名循环、过深别名链、缺失集合和不支持类型均产生脱敏告警，不污染其他变量。

## 图片处理

- 只接受已知 Figma、Figmausercontent、Amazon S3 和 CloudFront HTTPS 主机；
- 拒绝凭据、IP 地址、非 443 端口、片段和重定向；
- 同时检查 Content-Type、PNG/JPEG/WebP 魔数、PNG IHDR、尺寸和实际字节上限；
- 下载并发不超过 4，同一远端 URL 只下载一次；
- 资产和截图按 SHA-256 保存为不可变本地文件，重复内容复用同一文件。

### UISpec

- Schema 与受控组件目录版本；
- 多页面站内路由、受控节点树、状态、动作、视口和行为夹具；
- 不接受 JSX、脚本、外部 URL、任意 CSS 或未声明事件字段；
- 页面树必须无循环、无多父节点、无孤立节点，且每个节点只属于一个页面；
- 输入框、复选框、对话框和状态类型匹配；
- 行为步骤必须指向匹配的受控组件类型；
- 通过 `sourceDesignBundleRevision` 引用同项目当前 DesignBundle；
- 设计值和图片引用必须存在于当前 DesignBundle。

## 本地存储

项目布局：

```text
data/projects/<projectId>/
  project.json
  figma/
    current.json
    history/<revision>.json
    assets/
    screenshots/
  specs/
    current.json
    history/<revision>.json
```

写入协议：

1. 严格解析项目标识和草稿 Schema。
2. 获取每项目文件锁。
3. 读取并校验当前版本，比较 `baseRevision`。
4. 校验文档内部和跨文档引用。
5. 以同目录临时文件写入并执行文件 `fsync`。
6. 历史通过无覆盖硬链接发布，保证既有修订不可变。
7. current 通过原子重命名发布，并对目录执行 `fsync`。
8. 任一步骤失败时不覆盖上一份有效 current。

存储还会拒绝受管目录或文件上的符号链接，清理自身命名规则内的孤立临时文件，
复用内容一致的孤立历史，并回收已退出进程留下的写锁。图片并发测试暴露并修复了
“锁目录在回收检查与删除之间消失”的竞态；恢复锁期间新的获取者会等待。

## mock REST 纵向切片

集成测试通过注入式 `fetch` 模拟以下流程：

1. 读取 Figma 文件并发现两个页面；
2. 获取一个图片填充和两个页面截图；
3. 校验并保存三张本地图片；
4. Variables 返回 403；
5. 从 `fontSize` 绑定的已解析值生成脱敏设计值并回填节点引用；
6. 校验并发布 DesignBundle 修订 1；
7. 下一次核心文件请求返回 503，确认 `current.json` 仍为修订 1。

持久化结果不包含文件键明文、原始 Variable ID、签名 URL、Token 或上游错误正文。

## 剩余风险

- 崩溃恢复通过孤立历史和临时文件场景模拟，未执行真实进程强制终止故障注入；
- 并发测试覆盖同进程并发请求与 20 轮压力重复，尚未增加独立多进程压力测试；
- mock REST 与 M0 独立 live 探针尚未组合成真实文件的单次端到端检查；
- 失败检查可能留下未被 DesignBundle 引用的不可变内容哈希图片，当前不会覆盖有效
  修订，后续可在维护阶段增加基于引用的安全回收；
- Extension 的 `inspect_figma` 执行函数尚未接入 `FigmaInspector`，将在后续
  Agent Loop 接线阶段完成。
